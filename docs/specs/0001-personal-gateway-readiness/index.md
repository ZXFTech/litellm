# 0001. 个人模型网关完善计划

**Date**: 2026-11-18
**Status**: Proposed

## Summary

保留现有单实例网关，先让费用统计可信、客户端支出可控、数据能够恢复，再完善异常排查和日常维护。现有应用专用密钥、模型白名单、人民币账本与客户端取消处理可以继续使用。本计划依据源码和运行中服务的只读检查编写，实施步骤、参数建议和验收条件尚未执行

## Requirements

个人使用者需要把多个应用接到同一个入口，分别控制权限和支出，遇到失败时知道发生了什么，并能在主机或升级故障后恢复服务。当前以本机与局域网为规划基线，远程访问需求尚待确认

以下验收条件为本次提出的目标，不代表已获实施确认或已经通过

| 编号 | 完成条件 |
| --- | --- |
| AC-1 | 同一组固定用量在启动、目录刷新和部署更新后得到相同的已登记人民币费用，涵盖缓存、长上下文、priority、图片数量和分时价格。价格差异必须使预检失败，未验证的新模型不得授予客户端权限，不把未知费用显示为零 |
| AC-2 | 每个实际接入的应用有独立推理 Key、模型白名单、预算和并发上限。越权、到期、封禁、超限请求在到达上游前被拒绝，轮换后新 Key 可用且旧 Key 失效 |
| AC-3 | 数据库、原始加密盐及部署材料能够在独立环境恢复。备份失败不标记成功，恢复命令不能覆盖生产数据卷，至少完成一次从备份到可用网关的演练 |
| AC-4 | 实际客户端完成流式输出、工具调用、取消、超时和断线验收。一次图片操作不会因超时或恢复自动重复提交，交付不明保持待核查状态 |
| AC-5 | 一个无模型调用的诊断入口能区分服务、数据库、鉴权、模型配置和价格问题，返回脱敏结果。能够用请求 ID 关联应用记录与网关日志，无日志不能被解释为未调用或未计费 |
| AC-6 | 日志与备份有明确保留策略，定期任务能报告最近成功时间与失败原因。升级前在恢复副本上验证，失败时有与数据库状态匹配的回滚方案 |

## Decision

推荐在当前 LiteLLM、PostgreSQL、PowerShell 运维脚本和 agent-platform 接入上补齐上述能力。个人档继续使用一个 worker，暂不引入 Redis、多副本、组织管理或客户收款系统。网络规划先覆盖现有本机与局域网入口，跨网络接入单独确认后安排

这轮仅交付审计与实施计划。现有未提交的模型、价格、Compose 和测试改动属于基线的一部分，实施前必须重新核对归属和实际挂载版本

## Feature design

### 现有数据与接口

沿用 LiteLLM 的模型部署、虚拟 Key、spend logs 和预算累计数据，不新增业务数据库表。`local-gateway/pricing.json` 继续记录人民币定价，数据库保存部署配置，运行时价格由部署配置注册。官方目录只是模型参考资料，不能替代本地价格或供应商账单

运维动作沿用 `local-gateway/gateway.ps1` 作为入口。备份恢复与诊断逻辑可分别放在同目录的 `backup.ps1`、`diagnose.ps1`，避免把现有脚本扩成一个难以维护的大文件。新增文件仅在该实施阶段需要时创建

| 操作 | 复用表面 | 输出与权限边界 |
| --- | --- | --- |
| 检查服务 | GET `/health/readiness`、`/health/liveliness`、`/v1/models` | 就绪、数据库连接、可见模型。普通诊断不调用 `/health` 或管理页模型测试 |
| 检查定价 | GET `/model/info`、`/public/litellm_model_cost_map` | 按部署关联后的字段差异、币种、版本和校验结果。管理响应仅提取必要字段 |
| 管理客户端 | POST `/key/generate`、`/key/update`、`/key/block`、`/key/unblock` | 复用现有管理鉴权。普通 Key 只能调用已授权的推理路径 |
| 轮换 Key | 创建新 Key、客户端切换、验证、封禁旧 Key | 不依赖可能受许可限制的 regenerate 功能。切换失败时保留旧 Key 并撤销未用的新 Key |
| 备份与恢复 | 容器内 `pg_dump`、`pg_restore`，独立 Compose project | 备份清单、校验和、恢复报告。恢复目标必须为新建测试数据卷和本机备用端口 |
| 核查单次调用 | 现有调用日志与应用回执 | 关联 clientRequestId、gatewayCallId、sessionId、attemptId、operationId。初期复用管理页和只读诊断，不新建对外查询 API |

备份状态依次为创建中、校验通过、可供恢复，只有隔离恢复验收通过的备份才能标记为已验证。Key 轮换依次为新 Key 已创建、客户端已切换、验证通过、旧 Key 已封禁，不能先撤销仍在使用的唯一凭据

### Value sourcing

| 产出值 | 来源与规则 |
| --- | --- |
| 客户端清单、Key 别名与允许模型 | 以实际客户端清单为输入。已确认的基线只有 `agent-platform-local` 及其四个模型，不凭空新增设备或应用 |
| 预算金额 | 实施时输入 `budget_cny_per_30d`，必填且大于零，由用户可承受支出决定。多个 Key 的预算分配合计不得超过用户给出的总规划额度，这不是绝对支付余额保证 |
| 预算周期、并发、RPM、有效期 | 初始建议为滚动 30d、每 Key 并发 2、20 RPM、有效期 90d，均属于待应用的策略输入。先验证真实 agent 并发与请求规模，再按实际工作负载调整 |
| TPM 与模型输出上限 | 来自供应商账户额度、实际上下文规模和客户端单次任务要求。当前不把示例 100000 TPM 直接用于生产，防止误伤正常长上下文 |
| Key 到期提醒 | Key 的 expires 与检查时 UTC 时间之差，建议提前 7 天进入需轮换状态。单独记录预算周期，避免把 30d 当自然月 |
| 已确认费用与价格差异 | 当前登记价格、部署参数、模型元数据和实际计费路径共同校验。基础单价取 `litellm_params`，分时规则取 `model_info.off_peak_pricing`，比较忽略 JSON 字段顺序 |
| 时区与价格时段 | 取定价配置中的时区和窗口。供应商节假日及跨时段口径以其规则、账单为依据，未核实部分保留限制说明 |
| 请求关联和状态 | 应用生成的 clientRequestId、网关回执及 spend logs。缺少回执或日志表示证据不足，不能推导调用未发生 |
| 备份位置与访问控制 | 实施参数 `backup_root`，必须在仓库和同步工作目录之外。只允许当前操作者与恢复所需系统身份读取，异机副本须放在用户选定的加密存储中 |
| 备份清单 | 数据库快照、原 `.env`、价格和配置、镜像摘要、实际挂载文件及哈希、人民币 UI 产物、Git 提交与脏文件说明。不能仅用 Git 提交号代表当前部署 |
| 保留期限与恢复目标 | 建议日志明细 90d、备份每日一次并保留最近 7 份和每周 4 份，过期前先验证可恢复性。建议恢复点不超过 24h，恢复用时目标 1h，以演练结果决定是否达标 |
| 诊断结论 | 实际探测结果、配置对比和最近成功记录，统一区分 PASS、FAIL、NOT RUN、BLOCKED。报告不得包含 Key、供应商凭据或请求正文 |

金额、其他客户端清单、备份目的地及异机加密存储是实施前需要用户提供的输入，不影响本计划先行交付。以上建议值均没有写入当前运行配置

### Critical test scenarios

| 场景 | 验收重点 | 对应条件 |
| --- | --- | --- |
| 目录刷新、重启、部署更新 | 同一固定用量前后费用一致，完整保留分时规则、缓存与特殊档位，不使用供应商今日价格作为固定测试断言 | AC-1 |
| 价格漏配、字段漂移与仅数据库正确 | 被诊断识别，未验证部署不能开放给客户端，实际费用不能回落成错误币种 | AC-1、AC-5 |
| 越权、封禁、到期与超限 | 在隔离网关使用临时 Key 和本地协议服务，验证拒绝响应与上游请求数为零。并发槽在成功、异常和取消后释放 | AC-2 |
| 预算累计与重启 | 使用受控用量验证 CNY 费用进入累计、达到阈值拒绝、重启后不丢预算记录，并记录在途请求造成的超额窗口 | AC-1、AC-2 |
| 备份中断、损坏或凭据缺失 | 不生成成功标记，不覆盖生产数据卷。恢复模型、Key、凭据可解密性与账本汇总，恢复演练无付费上游调用 | AC-3 |
| 首包前断线、流式中断、取消、图片交付不明 | AP 到网关再到本地协议服务构造故障，记录每个 operation 的上游 POST 数，保留已有文本和未知状态 | AC-4、AC-5 |
| 实际客户端与供应商 | 每个实际使用的接口做最小真实请求，记录客户端操作、请求 ID、流式或图片结果及网关费用。自动化和模拟结果单独列出 | AC-4 |
| 日志清理与升级失败 | 先在恢复副本检查时间边界、累计预算与费用展示，再启用清理。用旧镜像、旧挂载与匹配数据库完成回滚演练 | AC-6 |

不以单元测试代替真实客户端验收，也不以一次真实请求证明所有异常路径。涉及失败注入、删除或数据库恢复的测试全部使用独立临时目录、端口、项目名与数据卷

## Build plan

按以下顺序交付，每一步都形成可以单独检查的结果

| 顺序 | 工作包与具体改动 | 交付与退出条件 | 对应条件 |
| --- | --- | --- | --- |
| P0-1 | 固化可恢复基线。扩展 `gateway.ps1` 的备份入口，实现 `backup.ps1`，保留原始盐、数据库、实际挂载与 UI，建立独立恢复环境 | 一份验证过的备份和恢复报告。未完成前不更换镜像、不改已有价格、不清理日志 | AC-3 |
| P0-2 | 排查运行时价格差异。跟踪 `get_model_cost_map.py`、Router 价格重注册、`litellm/utils.py` 与实际挂载版本，扩展现有 `test_gateway_pricing.py` 和对应上游回归测试 | 解释本次三个部署条目缺失及 DeepSeek 分时字段为空的原因，验证目录刷新、重启和实际计费路径。必要修复只针对确认根因，不用简单重启掩盖问题 | AC-1 |
| P0-3 | 配置个人支出和凭据策略。通过现有 Key 管理 API 设置预算、并发和 RPM，按客户端拆分 Key，完成轮换流程。在隔离环境验证版本支持与实际限制行为 | 现有 AP Key 受控，其他已确认客户端各有 Key，推理 Key 不能管理网关。更新前后配置留有脱敏记录，失败可恢复旧策略 | AC-2 |
| P1-1 | 完善新增模型与价格检查。添加 `diagnose.ps1` 的价格核对，接入 `gateway.ps1 verify`，为登记、部署、重启或刷新、验收、授予 Key 权限建立顺序清晰的操作步骤 | 漏价、错误层级、分时规则遗漏和实际计价不一致均可定位。通过检查后才授予客户端模型权限，历史费用不自动重算 | AC-1、AC-5 |
| P1-2 | 完成 AP 及实际客户端异常验收。先汇总当前 timeout 层级，再补流式、工具调用、取消、断线和图片未知结果验收；只修复确认的缺陷 | 接口兼容表与真实操作证据。AP 已有取消和禁止自动重试逻辑保留，其他协议只有通过验收才列为支持 | AC-4、AC-5 |
| P1-3 | 完善维护闭环。加入脱敏诊断、Key 到期与备份过期提示，配置系统定时备份，在副本验证日志清理，记录升级和回滚步骤 | 日常一条命令可查状态，备份任务失败可见，日志有经过验证的保留策略，完成一次升级和回滚演练 | AC-3、AC-5、AC-6 |

P0-1、P0-2、P0-3 组成个人档的第一批交付。P1-1 与 P1-2 在价格问题确认后可以并行，P1-3 的日志清理必须等待恢复演练和累计费用检查完成。每个工作包开始前重新拉取、检查工作树和运行版本，再确定其精确文件清单

AP 相关文件位于独立的 agent-platform 仓库，主要涉及 `src/server/model-gateway.ts`、`src/server/generate.ts`、`src/server/generate-images.ts` 及已有集成测试。该部分按独立仓库提交，不在本次网关计划提交中修改

## Migration plan

**Strategy** 为在现有服务上分步完善，先副本验证再切换，不重新导入模型和历史账本，不设计新的数据库 schema

**Phases** 为备份与恢复、修复已确认计价问题、逐个客户端设置策略、异常路径验收、启用定期维护。Key 切换保留短暂的新旧重叠窗口，每次只处理一个客户端

**Rollback** 为恢复本次变更前的配置或 Key 策略。涉及镜像和数据库迁移时，回退镜像、挂载、UI 与数据库必须成套匹配。生产切换前安排暂停新请求并等待在途请求结束，切换后若产生新写入，不得直接覆盖数据库并丢失记录

**Risks** 包括预算异步累计的超额窗口、单进程限流在重启时重置、主机休眠导致不可用、日志删除影响历史查询、备份携带敏感凭据，以及工作区文件与进程已加载版本不同。这些风险通过隔离演练、受控切换和清晰的结果状态处理

## Consequences

这条路线可以利用已实现的 LiteLLM 能力，优先减少个人支出失控、数据丢失和排障困难。代价是仍需维护本地价格与挂载补丁，备份和升级也需要持续验证

单机故障仍会中断服务，低并发策略也可能降低 agent 同时执行任务的速度。人民币账本用于个人成本管理，供应商账单仍是核对依据，预算不是绝对不会超出的预付余额

## Follow-up

远程访问尚未确认，若需要本人跨网络使用，另补私网或 HTTPS 接入与管理入口限制。当前未检查 Windows 防火墙实际规则，也未从另一台设备验收局域网边界

DeepSeek 法定节假日及跨时段请求的结算口径需要独立核对。当前只将它们列为精确对账限制，不宣称全年结算完全一致

凭据迁移脚本留下的临时文件需要先核对实际存在情况和 Windows ACL，再制定清理或轮换步骤。本次没有检查其内容、删除文件或断言发生了凭据泄漏

本计划尚无 scope 条目，实施任务以本文件为准。文档状态保持 Proposed，后续确认后再进入具体工作包
