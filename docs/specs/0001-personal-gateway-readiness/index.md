# 0001. 个人模型网关完善计划

**Date**: 2026-11-18
**Status**: Proposed

## Summary

保留现有单实例网关，先让费用统计可信、客户端支出可控、数据能够恢复，再完善异常排查和日常维护。现有应用专用密钥、模型白名单、人民币账本与客户端取消处理可以继续使用。本计划依据源码和运行中服务的只读检查编写，实施步骤、参数建议和验收条件尚未执行

## Requirements

个人使用者需要把多个应用接到同一个入口，分别控制权限和支出，遇到失败时知道发生了什么，并能在主机或升级故障后恢复服务。本轮接入范围为本机与局域网，管理页和管理 API 仅从网关主机访问

以下为实施验收条件。首批恢复、计费和 Key 换发方案已确认，各项结果在实施后分别记录

| 编号 | 完成条件 |
| --- | --- |
| AC-1 | 启动、目录刷新、重启和部署更新后，固定用量的实际 CNY 入账与独立计算的预期一致。首批同时完成各在用供应商计费产品的实扣账单对账，所有差额都有账单依据。价格差异必须使预检失败，未验证的新模型不得授予客户端权限，不把未知费用显示为零 |
| AC-2 | 每个实际接入的应用有独立推理 Key、模型白名单、预算和并发上限。越权、到期、封禁、超限请求在到达上游前被拒绝。常规换发在预算周期交界，验证旧 Key 已失效后才用新 Key。疑似泄漏立即封禁，周期内恢复必须延续可核对的剩余额度和原重置时间 |
| AC-3 | 分别完成同机新卷恢复和整机丢失恢复，两项都从备份恢复到可用网关。整机丢失演练在备用设备上使用独立保存的加密备份及解密材料，全程无需访问原主机和原硬盘。备份失败不标记成功，恢复命令不能覆盖正在使用的数据卷 |
| AC-4 | 实际客户端完成流式输出、工具调用、取消、超时和断线验收。一次图片操作不会因超时或恢复自动重复提交，交付不明保持待核查状态。网关主机可通过回环地址管理，局域网客户端只可达已开放的模型接口，无法访问管理路径 |
| AC-5 | 一个无模型调用的诊断入口能区分服务、数据库、鉴权、模型配置和价格问题，返回脱敏结果。能够用请求 ID 关联应用记录与网关日志，无日志不能被解释为未调用或未计费 |
| AC-6 | 日志与备份有明确保留策略，定期任务能报告最近成功时间与失败原因。升级前在恢复副本上验证，失败时有与数据库状态匹配的回滚方案 |

## Decision

推荐在当前 LiteLLM、PostgreSQL、PowerShell 运维脚本和 agent-platform 接入上补齐上述能力。个人档继续使用一个 worker，暂不引入 Redis、多副本、组织管理或客户收款系统

这轮仅交付审计与实施计划。现有未提交的模型、价格、Compose 和测试改动属于基线的一部分，实施前必须重新核对归属和实际挂载版本

## Rationale

检查证据、现有能力、缺口分类与方案取舍见 [审计依据](rationale.md)，实施前要定下的事项见 [独立复核](rationale.md#独立复核)

## Feature design

### 现有数据与接口

沿用 LiteLLM 的模型部署、虚拟 Key、spend logs 和预算累计数据，不新增业务数据库表。`local-gateway/pricing.json` 继续记录人民币定价，数据库保存部署配置，运行时价格由部署配置注册。官方目录只是模型参考资料，不能替代本地价格或供应商账单

运维动作沿用 `local-gateway/gateway.ps1` 作为入口。备份恢复与诊断逻辑可分别放在同目录的 `backup.ps1`、`diagnose.ps1`，避免把现有脚本扩成一个难以维护的大文件。新增文件仅在该实施阶段需要时创建

| 操作 | 复用表面 | 输出与权限边界 |
| --- | --- | --- |
| 检查服务 | GET `/health/readiness`、`/health/liveliness`、`/v1/models` | 就绪、数据库连接、可见模型。普通诊断不调用 `/health` 或管理页模型测试 |
| 检查定价 | GET `/model/info`、`/public/litellm_model_cost_map` | 按部署关联后的字段差异、币种、版本和校验结果。管理响应仅提取必要字段 |
| 管理客户端 | POST `/key/generate`、`/key/update`、`/key/block`、`/key/unblock` | 管理员从网关主机通过回环地址调用，复用现有管理鉴权 |
| 调用模型 | 按客户端所需协议开放模型发现和推理接口 | 使用应用推理 Key。局域网入口只转发允许的路径和方法 |
| 换发 Key | 暂停客户端请求、封禁旧 Key、创建并验证新 Key、切换客户端 | 使用现有 Key 管理接口。常规按预算周期交界换发，疑似泄漏时先封禁 |
| 备份与恢复 | 容器内 `pg_dump`、`pg_restore`，独立 Compose project | 备份清单、校验和，以及同机和整机丢失演练报告。两个恢复目标都使用新测试数据卷与各自的回环端口 |
| 核查单次调用 | 现有调用日志与应用回执 | 关联 clientRequestId、gatewayCallId、sessionId、attemptId、operationId。初期复用管理页和只读诊断，不新建对外查询 API |

备份状态依次为创建中、校验通过、可供恢复，只有隔离恢复验收通过的备份才能标记为已验证

### 首批恢复演练

同机演练在原主机上用新项目和新数据卷验证。整机丢失演练在备用主机或运行在另一台设备的干净虚拟机上进行，假设原主机与硬盘不可用。备用环境从独立存储取得加密备份，并能独立取得解密材料、镜像和部署所需文件

启动前核对实际数据库目标、数据卷、可写挂载和监听地址，并限制恢复副本访问真实上游。两次演练都用备份点的脱敏摘要核对模型映射、Key 授权与封禁状态、费用汇总，验证原始加密盐能解密备份中的供应商凭据。分别记录恢复点和恢复用时，两项均通过后才完成 AC-3

### 首批计费验收

网关入账验算使用冻结版本的 `pricing.json`、固定用量和计价时刻。用独立计算得出预期 CNY 金额，让隔离网关接收本地上游返回的可控用量，按请求 ID 核对持久化的费用记录。在相同价格版本下，启动、目录刷新、重启和部署更新后都应得出相同金额。若更新本身调整了定价，则改用新版本的预期。确认零元、未确认和金额缺失分别记录

供应商实扣对账覆盖各在用计费账户和产品的已结算样本。优先使用能对应本次部署与价格版本的既有账单和调用记录。若缺少匹配样本，实施时再确定最小真实请求及费用上限。供应商有逐笔明细时按请求关联。只有汇总时，使用可确定所含调用的独立结算时段，按账户、产品、用量单位、时区和币种对齐

对账记录分别列网关金额、供应商用量费用、优惠或抵扣及最终实扣。相同口径的用量费用须一致，账单精度和已列明的扣费调整须可复算。用量或费用不符记为 `FAIL`，待结算或无法归属记为 `BLOCKED`，并保留网关验算的独立结果。两项都通过后才完成 P0-2

### 首批密钥换发

常规换发按现有 Key 的实际预算重置时间安排，提前确认 Key 有效期覆盖切换窗口。暂停该客户端的新请求，等待在途请求结束并核对费用。确认旧 Key 已封禁且拒绝请求，并核对已进入新预算周期后，为同一应用启用新 Key，核对模型权限、新周期额度和下次实际重置时间

疑似泄漏时立即封禁旧 Key，再处理在途请求和费用。周期内只有在核清剩余额度、确认能保留原重置时间且实际限制生效后，才允许新 Key 恢复调用。其余情况暂停该客户端至原预算周期结束。常规切换失败先封禁新 Key，只有旧 Key 安全有效且本周期剩余额度能核对并延续时才恢复旧 Key。疑似泄漏的凭据保持封禁

### 本机管理与局域网推理

P1-2 将管理与推理入口分开。LiteLLM 的宿主监听保留在回环地址，局域网监听改由单独的推理入口提供。按实际客户端需要明确允许转发的路径和 HTTP 方法，其余请求在入口处拒绝，包括 `/ui/` 与管理 API。Windows 防火墙限定可访问推理入口的局域网范围，入口负责区分请求路径

从网关主机验证管理员能在本机打开管理页并使用管理 API，从另一台受信设备用推理 Key 验证模型调用和管理路径被挡住。同时核对 LAN 上不存在直达 LiteLLM 的旧端口映射。若 agent-platform 运行在其他设备上，其网关地址还需满足客户端的 HTTPS 校验

### Value sourcing

| 产出值 | 来源与规则 |
| --- | --- |
| 客户端清单、Key 别名与允许模型 | 以实际客户端清单为输入。已确认的基线只有 `agent-platform-local` 及其四个模型，不凭空新增设备或应用 |
| 局域网接口及允许来源 | 允许的请求路径和方法取自实际客户端协议和网关接口。监听地址及允许来源来自网关实际局域网地址和实施时确认的 Windows 防火墙范围 |
| 预算金额 | 实施时输入 `budget_cny_per_30d`，必填且大于零，由用户可承受支出决定。多个 Key 的预算分配合计不得超过用户给出的总规划额度，这不是绝对支付余额保证 |
| 预算周期、并发、RPM、有效期 | 初始建议为每 30d 定期重置预算、每 Key 并发 2、20 RPM、有效期 90d，均属于待应用的策略输入。先验证实际重置时间、agent 并发与请求规模，再按实际工作负载调整 |
| TPM 与模型输出上限 | 来自供应商账户额度、实际上下文规模和客户端单次任务要求。当前不把示例 100000 TPM 直接用于生产，防止误伤正常长上下文 |
| Key 到期提醒 | Key 的 expires 与检查时 UTC 时间之差，建议提前 7 天进入需轮换状态。单独记录预算周期，避免把 30d 当自然月 |
| 换发时剩余额度和周期交界 | 从现有 Key 的 `budget_reset_at` 取得原重置时间，用该应用本周期的预算减去已核清的 CNY 支出计算剩余额度，最低为零。在途费用未确认时缺少可用余额结论 |
| 网关应计、实记费用与差异 | 应计取定价版本与测试用量的独立计算，实记取关联到该次调用的持久化费用记录。部署的基础单价取 `litellm_params`，分时规则取 `model_info.off_peak_pricing`，比较忽略 JSON 字段顺序 |
| 供应商实际扣费与差异 | 取实际计费账户的已结算账单，按同一用量范围与网关日志匹配。优惠、抵扣、其他差额及结算精度以可核对的账单项目为依据，验收记录使用脱敏摘要 |
| 时区与价格时段 | 取定价配置中的时区和窗口。供应商节假日及跨时段口径以其规则、账单为依据，未核实部分保留限制说明 |
| 请求关联和状态 | 应用生成的 clientRequestId、网关回执及 spend logs。缺少回执或日志表示证据不足，不能推导调用未发生 |
| 备份位置与访问控制 | 实施参数 `backup_root`，必须在仓库和同步工作目录之外。只允许当前操作者与恢复所需系统身份读取。整机丢失恢复使用用户选定的独立存储和备用设备，备份加密，解密材料可从原主机之外单独取得 |
| 备份清单 | 数据库快照、原 `.env`、价格和配置、镜像摘要、实际挂载文件及哈希、人民币 UI 产物、Git 提交与脏文件说明。不能仅用 Git 提交号代表当前部署 |
| 保留期限与恢复目标 | 建议日志明细 90d、备份每日一次并保留最近 7 份和每周 4 份，过期前先验证可恢复性。建议恢复点不超过 24h，恢复用时目标 1h，以演练结果决定是否达标 |
| 诊断结论 | 实际探测结果、配置对比和最近成功记录，统一区分 PASS、FAIL、NOT RUN、BLOCKED。报告不得包含 Key、供应商凭据或请求正文 |

金额、其他客户端清单、备份位置和备用恢复设备在对应工作包开始前确认。以上建议值均没有写入当前运行配置

### Critical test scenarios

| 场景 | 验收重点 | 对应条件 |
| --- | --- | --- |
| 启动、目录刷新、重启、部署更新 | 隔离网关实际入账与独立计算一致，覆盖模型适用的缓存、长上下文、priority、图片数量和分时价格，测试依据为冻结的定价版本 | AC-1 |
| 供应商已结算账单对账 | 用量和费用能对应到网关记录，报告用量费用、最终实扣和可复算差额。结算未完成或无法匹配的样本不能算通过 | AC-1 |
| 价格漏配、字段漂移与仅数据库正确 | 被诊断识别，未验证部署不能开放给客户端，实际费用不能回落成错误币种 | AC-1、AC-5 |
| 越权、封禁、到期与超限 | 在隔离网关使用临时 Key 和本地协议服务，验证拒绝响应与上游请求数为零。并发槽在成功、异常和取消后释放 | AC-2 |
| 预算累计与重启 | 使用受控用量验证 CNY 费用进入累计、达到阈值拒绝、重启后不丢预算记录，并记录在途请求造成的超额窗口 | AC-1、AC-2 |
| 已用部分预算后换发 Key | 常规路径到重置点才开放新周期额度，验证旧 Key 已失效。疑似泄漏立即封禁，在费用未核清或无法保留原重置时间的情况下保持暂停。若周期内恢复，验证只可使用原余额且按原时间重置 | AC-2 |
| 同机恢复与整机丢失 | 分别从同机备份与独立存储上的加密副本恢复。整机丢失场景无法从原主机补取任何材料。两套恢复环境均完成备份点状态核对，无付费上游调用 | AC-3 |
| 备份中断、损坏或凭据缺失 | 不生成成功标记。实际库、数据卷或挂载目标与当前服务冲突时，恢复入口必须在写入前拒绝 | AC-3 |
| 首包前断线、流式中断、取消、图片交付不明 | AP 到网关再到本地协议服务构造故障，记录每个 operation 的上游 POST 数，保留已有文本和未知状态 | AC-4、AC-5 |
| 实际客户端与供应商 | 每个实际使用的接口做最小真实请求，记录客户端操作、请求 ID、流式或图片结果及网关费用。自动化和模拟结果单独列出 | AC-4 |
| 本机管理与局域网推理 | 从本机管理页和管理 API 验证管理员可用，从另一台受信设备验证推理可用且管理路径不被转发。检查旧直连映射已移除和防火墙范围实际生效 | AC-4 |
| 日志清理与升级失败 | 先在恢复副本检查时间边界、累计预算与费用展示，再启用清理。用旧镜像、旧挂载与匹配数据库完成回滚演练 | AC-6 |

不以单元测试代替真实客户端验收，也不以一次真实请求证明所有异常路径。涉及失败注入、删除或数据库恢复的测试全部使用独立临时目录、端口、项目名与数据卷

## Build plan

按以下顺序交付，每一步都形成可以单独检查的结果

| 顺序 | 工作包与具体改动 | 交付与退出条件 | 对应条件 |
| --- | --- | --- | --- |
| P0-1 | 固化可恢复基线。扩展 `gateway.ps1` 的备份入口，实现 `backup.ps1`，保留原始盐、数据库、实际挂载与 UI，制作独立保存的加密副本，分别做同机及整机丢失恢复演练 | 两项演练均通过，交付验证过的备份和两份结果。未完成前不更换镜像、不改已有价格、不清理日志 | AC-3 |
| P0-2 | 排查运行时价格差异。跟踪 `get_model_cost_map.py`、Router 价格重注册、`litellm/utils.py` 与实际挂载版本，扩展现有 `test_gateway_pricing.py` 和对应上游回归测试 | 解释本次三个部署条目缺失及 DeepSeek 分时字段为空的原因。交付各变更场景下的网关入账验算及供应商实扣账单对账，两项均通过 | AC-1 |
| P0-3 | 配置个人支出和凭据策略。通过现有 Key 管理 API 设置预算、并发和 RPM，按客户端拆分 Key。在隔离环境验收周期交界换发、泄漏封禁与剩余额度保护 | 现有 AP Key 受控，其他已确认客户端各有 Key，推理 Key 不能管理网关。常规换发与疑似泄漏路径通过，更新前后配置留有脱敏记录 | AC-2 |

## Migration plan

**Strategy** 为在现有服务上分步完善，先副本验证再切换，不重新导入模型和历史账本，不设计新的数据库 schema

**Phases** 为备份与恢复、修复已确认计价问题、逐个客户端设置策略、异常路径验收、启用定期维护。每次换发处理一个客户端，旧 Key 封禁生效后再启用新 Key

**Rollback** 为恢复本次变更前的配置或 Key 策略。涉及镜像和数据库迁移时，回退镜像、挂载、UI 与数据库必须成套匹配。生产切换前安排暂停新请求并等待在途请求结束，切换后若产生新写入，不得直接覆盖数据库并丢失记录

**Risks** 包括预算异步累计的超额窗口、单进程限流在重启时重置、主机休眠导致不可用、日志删除影响历史查询、备份携带敏感凭据，以及工作区文件与进程已加载版本不同。这些风险通过隔离演练、受控切换和清晰的结果状态处理

## Consequences

这条路线可以利用已实现的 LiteLLM 能力，优先减少个人支出失控、数据丢失和排障困难。代价是仍需维护本地价格与挂载补丁，备份和升级也需要持续验证

单机故障仍会中断服务，低并发策略也可能降低 agent 同时执行任务的速度。人民币账本用于个人成本管理，供应商账单仍是核对依据，预算不是绝对不会超出的预付余额
