检查日期为 2026-11-18。运行状态和工作树会继续变化，实施前必须重新核对。模型名称在本文表示当时已部署的对象，不代表推荐继续使用某个供应商版本

### AP 已有行为

`src/server/model-gateway.ts` 校验网关地址并附加请求关联信息，在读取响应体之前保存可用的网关回执。`src/server/generate.ts` 的摘要调用预算为 120 秒、文本回复为 300 秒、首内容等待为 90 秒、流空闲为 60 秒，并有周期性的取消和任务所有权检查。这些是客户端代码值，不代表所有供应商的服务时限

`src/server/generate-images.ts` 为图片操作设置 5 分钟预算，并在提交前记录可恢复的状态。结果不明时不自动重复提交。客户端取消不能保证供应商已经停止生成或不再计费

历史文档记载部分真实文本和图片调用通过，以及请求回执和 CNY 关联验证。本次没有重跑这些用例，因此将其列为历史证据，不当作本轮 PASS

### 单实例 Key 能力

当前版本对应源码已有 Key 预算、有效期、RPM、TPM 和并发限制路径，单 worker 可以使用进程内限流。进程内状态不能用于多 worker 共享，重启也可能重置短周期计数。基础 Key 控制与受许可限制的按模型预算、部分轮换功能应分开看待

实施时仍要用实际镜像和独立临时 Key 验证限制生效、缓存刷新、取消释放以及预算累计。无 Redis 的部署不直接套用需要共享存储的 fail-closed 限流参数

## Options considered

### 在现有系统上补齐

保留现有接口、模型和历史数据，增加价格回归、Key 策略、运维脚本与客户端验收。优势是复用已投入使用的能力，变化范围小。代价是继续维护固定镜像与本地挂载的组合，升级需要验证这套组合

### 并行建设第二套网关并逐步迁移

可以为长期迁移到常在线主机建立独立环境，逐个切换客户端。优势是隔离生产试验，代价是维护两套部署、配置和可能分散的账本。当前采用独立环境做恢复及故障测试即可，不需要长期运行两套网关

### 直接替换部署或重建管理平台

可以统一新的技术路线和界面，但需要重新验证图片适配、人民币账本、请求关联、密钥和历史数据。成本与迁移风险高，现有证据没有显示这些替换能够比补齐当前能力更快解决个人使用问题

## Rationale

当前问题主要在可验证性和运维闭环。现有数据库、虚拟 Key、日志和客户端已经提供主体能力，继续使用它们可以让每个工作包直接对应可观测的改善

优先做恢复基线，是因为价格配置、Key 策略和日志保留都会影响已有服务。随后检查实际计费，再配置预算，可以避免把尚未验证的费用统计当作可靠的支出控制基础

个人档接受单机停机影响，暂不引入高可用基础设施。真实流量、客户端数量或可用性要求变化后，再评估远程入口、常在线主机和多实例协调
