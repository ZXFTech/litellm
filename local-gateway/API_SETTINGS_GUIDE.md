# 网关 API 设置建议

适用于个人多设备与 agent-platform、内部多应用多团队、对外付费 API 三种场景。当前网关基于 LiteLLM v1.108.3，以下部署和参数建议需要按场景实施，目录刷新不会自动启用这些能力

## 三种场景的选择

| 项目 | 个人多设备与 agent-platform | 内部多应用多团队 | 对外付费 API |
| --- | --- | --- | --- |
| 入口 | 局域网或私网，跨网络使用 HTTPS | 稳定 HTTPS 域名，区分开发和生产 | 独立公开 HTTPS API 域名，管理入口私有 |
| 身份边界 | 每设备或应用独立虚拟 Key | 每团队预算，每应用每环境独立 Key | 每客户可信租户映射，每应用独立 Key |
| 模型开放范围 | 明确列出需要的公共模型名 | 按团队和应用授权，受控升级 | 公布版本化模型目录与能力，明确变更规则 |
| 预算 | 每 Key 设置可承受的支出额度 | 团队总额加应用子额度 | 套餐额度与独立账务控制，预留未完成请求的成本 |
| 限流 | 低并发起步，防止 agent 失控循环 | 团队、Key、部署三级核算 | 租户公平性、短周期限速、并发与请求大小共同控制 |
| 部署 | 单实例可满足低流量，接受主机停机影响 | 常在线服务器，多实例共享状态 | 网关与数据服务消除单点，恢复演练后再承诺可用性 |
| 费用用途 | 个人成本统计 | 部门分摊和预算治理 | 可审计的客户计量、对账、退款与冲正 |

LiteLLM 的虚拟 Key、预算、限流和基础费用统计提供这些方案的基础能力。团队边界与角色管理需要结合当前版本和许可配置，参见 [虚拟 Key](https://docs.litellm.ai/docs/proxy/virtual_keys) 与 [多租户架构](https://docs.litellm.ai/docs/proxy/multi_tenant_architecture)

## 所有场景共用的 API 约定

| 设置 | 建议 |
| --- | --- |
| 客户端 Base URL | OpenAI 兼容客户端使用网关地址加 /v1，当前局域网地址为 http://192.168.0.205:4000/v1。其他协议客户端按其接口规则配置，避免重复拼接 /v1 |
| 上游 API Base | 在模型部署中填写供应商地址，客户端无需知道供应商连接信息 |
| 客户端 API Key | 使用限定权限的虚拟 Key。master key 只供管理操作，供应商 Key 只保留在网关侧 |
| Public Model Name | 使用稳定公共名称，同时保留可复现的固定版本名称。切换上游前验证工具调用、流式输出、上下文与计费行为 |
| models | 明确列出允许调用的公共模型名。生产服务不采用无限开放的通配模型权限 |
| allowed_routes | 将应用凭据限制为所需推理路径，并验证无法访问管理接口。不要依赖 Key 名称判断权限 |
| 请求关联 | 服务端生成请求 ID，关联应用、环境、团队、session 和 attempt。外部传入的 user 或 metadata 仅作业务标签，不能决定租户或付款方 |
| 错误处理 | 区分认证失败、权限不足、限流、预算不足、供应商故障、流中断和交付结果不明，保留可查的请求 ID |
| 超时 | 分别设定连接、单次调用、流式等待与整个操作的时间预算，外层超时应容纳内层收尾，不要让多个层级独立无限等待 |
| 敏感数据 | 默认记录调用元数据，正文日志按用途单独开启并设保留期限。浏览器前端不嵌入服务端长期 Key |

公共模型名对应上游部署的映射由网关维护。模型能力、公共名称与价格配置应一起版本化，参见 [模型管理](https://docs.litellm.ai/docs/proxy/model_management)

## 个人多设备与 agent-platform

当前可继续采用单实例，优先把客户端凭据拆开。agent-platform、开发工具和其他设备分别使用虚拟 Key，设置模型白名单，泄漏或停用某个客户端时可以单独撤销。需要外网访问时先建立私网或 HTTPS 入口，不直接把管理端口暴露到公网

以下是一个低流量试运行的 Key 配置示例。假设这个应用每 30 天可承受人民币 50 元费用，每分钟预计不超过 20 个请求与 100,000 token，最多同时进行 2 个请求。数值用于说明设置方法，应按实际工作负载调整，公共模型名需要替换为已部署且登记价格的名称

~~~json
{
  "key_alias": "agent-platform-dev",
  "models": ["<已部署公共模型名>"],
  "max_budget": 50,
  "budget_duration": "30d",
  "rpm_limit": 20,
  "tpm_limit": 100000,
  "max_parallel_requests": 2,
  "duration": "90d"
}
~~~

这是管理员创建虚拟 Key 时的示例请求体，不能直接作为模型的 LiteLLM Params。duration 是 Key 的有效期，budget_duration 是预算周期，二者独立。30d 是时长，不等同于自然月账期。示例金额只有在本项目统一人民币价格的前提下才能按人民币解释

初期保留当前零重试和零 fallback 策略，由应用统一决定是否重试。图片生成出现交付不明时先查询状态或由用户决定，避免自动重复生成。数据库与原始加密盐需要一并备份，电脑休眠和关机会使服务不可用。预算检查存在并发和统计更新的时间窗口，应配合并发限制使用，不能把示例预算视为绝对不会超出的支付余额

## 内部多应用多团队

Team 对应实际成本负责人或业务部门，Key 对应应用与环境。团队设置总预算，各应用分配子额度；开发、测试和生产使用独立凭据与模型访问范围。统一管理员可以先管理基础 Teams，委派团队管理员和更高层 Organizations 要单独核对许可

网关迁移到常在线服务器，至少两个实例共享 PostgreSQL 和 Redis，并置于 HTTPS 负载均衡后。Redis 用于跨实例限流、路由状态等协调，可以继续关闭响应缓存。仅增加网关副本不能解决数据库、Redis 或单一供应商的故障。数据库连接池按最大实例数、每实例 worker 数、滚动发布重叠和运维连接共同计算，参见 [生产部署建议](https://docs.litellm.ai/docs/proxy/prod) 与 [Redis 容量规划](https://docs.litellm.ai/docs/proxy/redis_sizing)

模型部署的 rpm 和 tpm 按供应商真实额度配置，Key 与 Team 的 rpm_limit 和 tpm_limit 用于分配内部额度。并发上限还要考虑请求耗时，不能只看每分钟请求数。用量估算应覆盖输入、预期输出、峰值流量与额外尝试次数，并保留容量余量。上线值由代表性请求、并发压测和供应商限制共同决定

重试只由一个明确层级负责，按可重试错误、总时限和最大尝试数控制。备用模型需要通过能力与数据区域验证，不能仅因为价格接近就互相替换。流已经输出一部分内容后，不应把新模型的完整重试流直接拼到旧流后。配置入口见 [超时](https://docs.litellm.ai/docs/proxy/timeout) 和 [fallback](https://docs.litellm.ai/docs/proxy/reliability)

监控按应用、团队和模型区分成功率、429、供应商错误、首 token 延迟、P95 与 P99 延迟、活跃并发、token 分类、费用及预算余量。服务外部还需要监测网关不可达，费用写入延迟和数据库异常应能告警。日志默认不保存正文，排障采样需控制访问和保留期限，指标接入可参考 [Prometheus](https://docs.litellm.ai/docs/proxy/prometheus)

## 对外付费 API

在内部多团队方案之上增加独立的客户身份与账务层。根据已认证 Key 在服务端解析客户，不接受客户端通过任意 user、team_id 或 metadata 选择扣费主体。公开入口只开放产品承诺的推理接口和必要模型查询，管理 UI、Key 管理、模型管理及调试接口保留在私网

入口应限制请求体大小、输出上限、连接数和每租户并发。SSE 流式响应需要端到端验证代理缓冲、空闲超时、客户端取消和断线后的行为。先完成故障与容量验收，再制定可用性目标，不能用网关副本数量直接推导 SLA

客户售价、供应商成本和支付余额分别建模。用量事件至少包含可信客户 ID、请求与尝试 ID、实际模型、用量分类、计费版本、币种、状态和时间。账务层需要幂等入账、余额预留与结算、退款和冲正、供应商对账以及差异处理。LiteLLM spend 可作为计量输入，不能单独承担完整收款账本，参见 [账单集成](https://docs.litellm.ai/docs/proxy/billing)

预付费场景需要考虑同时在途请求的预计成本。使用原子预留与结束后结算控制余额，超额输出、失败、流中断、缓存优惠、图片实际数量和交付结果不明都应有明确计费规则。重试同一业务操作必须有业务幂等记录，不应假设所有供应商都支持同一种幂等请求头

预算或租户状态无法确认时，应拒绝新的计费请求并返回可诊断错误。数据库或 Redis 失联时的策略需要演练，不将自动放行当作公网计费服务的默认降级方式。提供备用模型前向客户说明版本、质量、数据区域和价格变化，按客户允许的范围路由

密钥轮换、撤销、异常流量响应和恢复演练应进入运行流程。对外账单的币种、汇率与价格版本固定在计量事件上，历史数据不能随最新模型参考价重新解释。本项目当前人民币回调和单一账本需要进一步设计后才能承担多客户商业结算

## 人民币价格与新模型接入

当前调用前回调要求公共模型名存在于 pricing.json。界面保存模型、刷新 LiteLLM 官方目录、向客户端 Key 授权，是相互独立的操作。新增模型需要同时维护数据库部署价格和本地价格登记，重启使回调加载更新，再用真实请求核对日志金额

界面标准价格输入框使用每百万 token，LiteLLM Params 的 input_cost_per_token 等原始字段使用每个 token。缓存读写、长上下文、时段和服务等级应分别覆盖，图片按实际交付数量处理。供应商美元参考价格不能直接加入当前人民币账本，官方目录价格也不代表供应商账单已完成对账，参见 [自定义定价](https://docs.litellm.ai/docs/proxy/custom_pricing) 和本项目 [人民币计费说明](PRICING.md)

目录更新应与部署价格变更分开发布。先保存目录修订及部署价格快照，再刷新并比较结果。模型目录只解决收录问题，新接口能力需要验证适配器，当前部署固定在 v1.108.3，更新目录不会升级 Python 运行时或管理 API

## 版本与企业许可边界

基础虚拟 Key、预算、限流与费用统计可在开源网关中使用。Organizations、委派组织或团队管理员、企业审计、SCIM、部分 SSO 和其他高级管理能力需要按部署版本与有效许可核对。企业级运行要求可以分阶段建设，购买许可也不能替代备份、容量测试和故障恢复，功能范围见 [LiteLLM Enterprise](https://docs.litellm.ai/docs/enterprise)

当前本地 organization_endpoints.py 对整个 Organizations 路由检查企业许可，团队管理员授权也有 premium 检查。官网新 Customer Management 标注从 v1.111 起提供，不能作为当前 v1.108.3 的现有能力，参见 [虚拟 Key 文档](https://docs.litellm.ai/docs/proxy/virtual_keys)

升级应在隔离环境验证数据库迁移、镜像摘要、Python 挂载路径、定制计费、管理界面与客户端兼容性。当前多个源码文件以只读挂载覆盖官方镜像，版本升级时必须逐项复核

## 实施顺序与验收

| 阶段 | 建议动作 | 完成条件 |
| --- | --- | --- |
| 个人基线 | 拆分虚拟 Key，明确模型权限、预算、并发与超时，安排备份 | 未授权模型和管理路径被拒绝，Key 可单独撤销，备份可恢复 |
| 内部服务 | HTTPS 与私有管理入口，常在线多实例，Redis 协调，团队额度与监控 | 跨实例限流一致，配置在约定时间内收敛，单实例故障可继续服务 |
| 商业服务 | 客户身份映射、计量事件、账务预留结算、公开 API 契约 | 并发扣费不重复，失败与未知交付可追踪，客户隔离和对账通过 |

每个阶段都验证普通与流式调用、工具调用、供应商限流、超时、客户端断线、依赖故障及价格计算。多实例阶段增加 Redis 与数据库失联测试，商业阶段增加余额不足、重复请求、退款冲正和租户越权测试。当前目录刷新仅完成目录数据更新与配置快照核对
